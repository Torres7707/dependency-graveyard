# 性能优化记录：墓园页滚动卡顿

2026-11-13。问题：查询完成后上下滚动明显卡顿；有些墓碑滑走再滑回来是空白，过一会才重新出现。

## 结论

问题主要出在动效设计和写法上，Motion 库本身不是瓶颈。

- 页面同时跑着约 171 个无限循环动画：每个墓碑图标的每个部件（火苗、光晕、火星、手指、尘土、眼睛……）各自循环，场景层又有约 100 个（70 颗星星各自闪烁、22 只萤火虫、蝙蝠、云、雾）。
- 每个动画元素都会被提升为一个合成层，空闲时页面有 172 个层。
- 其中一部分动画属性不能交给合成线程：幽灵尾巴的 `d` 路径插值，SVG 子元素上的 CSS `opacity`（星星），`pathLength`。只要有一个这类动画在跑，主线程就要每帧重做 BeginMainFrame → Layerize → Paint。
- 合成线程被 172 个层占满，光栅化跟不上滚动。滑回来的墓碑 DOM 一直在、`opacity` 也是 1，只是对应图块还没画出来，所以看起来“消失了”。
- Motion 自身的 JS 只占主线程时间约 8%，`filter` 几乎不占。

## 测量方法

- 生产构建：`pnpm build && pnpm preview`，Playwright 驱动 headless Chromium，视口 1280×800。
- **滚动帧时间**：粘贴 60 个依赖的 manifest（低于轻量模式阈值 80），CPU 降速 4×，用 rAF 记录先向下滚到底、再滚回顶部的每帧间隔。
- **空闲 trace**：打开示例墓园，滚到 300px，不降速录 3 秒 trace，按线程统计任务时间，并用 `LayerTree` 统计层数。
- **“消失”检查**：滚到底再滚回来，150 ms 后截图，同时检查视口内墓碑的 `opacity`。
- 对照组：用顶栏“暂停动效”关掉所有动画后再测一遍。

注意：headless Chromium 用软件合成，VizCompositor 线程的绝对数值比真实 GPU 高，只适合前后对比。测量脚本在仓库外（`/tmp/dgprof/`），没有提交。

## 改了什么

| 改动 | 文件 | 原因 |
|---|---|---|
| 循环名额：同一时间最多 `LOOP_BUDGET = 8` 个图标循环（离视口中心最近的可见墓碑），滚动时全部暂停，停止滚动 `SCROLL_IDLE_MS = 180` 后恢复 | `src/graves/motionBudget.ts`、`src/domain/config.ts`、`Tombstone.tsx` | 让成本不随墓碑数量增长；滚动期间把帧预算全部留给滚动和光栅化 |
| 每个图标只保留一个整体循环，部件动作改成只在悬停/聚焦时播放 | `src/graves/icons/*Icon.tsx` | 每个图标从 4–10 个循环降到 1 个 |
| 幽灵尾巴 `d` 插值、眼睛、光点改为悬停才动 | `GhostIcon.tsx` | `d` 不能在合成线程运行，会让主线程每帧重绘 |
| 去掉活体蜡烛每个实例各自的 `feGaussianBlur` 滤镜，改为半透明描边光晕 | `AliveIcon.tsx` | 每个墓碑都带一份滤镜，且会被循环反复重绘 |
| 僵尸手指、乌鸦翅膀、火星改为悬停动作；尘土、光点改为静态 | `ZombieIcon.tsx`、`BuriedIcon.tsx`、`AliveIcon.tsx`、`LostIcon.tsx` | 同上 |
| 僵尸土块的 `animate` 目标不再随循环名额变化 | `ZombieIcon.tsx` | 之前每次拿到或失去名额都会重放入场动画，有几个动画一直停在运行状态 |
| 星星：70 个 SVG 圆各自闪烁 → 一层静态 + 一层整体闪烁（约 1/3 的星星） | `Scene.tsx`、`index.css` | 动 SVG 子元素会重绘整片天空；整层 `opacity` 可以在合成线程运行 |
| 萤火虫 22 → 8 | `Scene.tsx` | 每只都是一个合成层 |
| 蝙蝠：两片翅膀各自旋转 → 整个 `<svg>` 做 `scaleY` 扇动 | `Scene.tsx`、`index.css` | SVG 内部变换在主线程执行，整个元素的变换可以交给合成线程 |

没有改：轻量模式阈值（仍为 80）、`content-visibility`、减弱动效和“暂停动效”的行为。

## 前后对比

60 个依赖，4× CPU 降速，滚动帧时间（ms）：

| | p50 | p90 | p99 | 长帧 |
|---|---|---|---|---|
| 优化前 | 83 | 134 | — | 大部分帧 |
| 优化后（3 次） | 16.7–17.0 | 33.2–33.9 | 50–66 | 3–11 / ~330 |
| 关闭所有动效（下限） | 16.7 | 18.5 | — | — |

示例墓园，空闲 3 秒，不降速：

| | 层数 | 运行中的动画 | 主线程 | 其中 BeginMainFrame / Layerize / Paint | 合成线程（Compositor） | VizCompositor |
|---|---|---|---|---|---|---|
| 优化前 | 172 | 171 | 2210 ms | 1053 / 433 / 209 | 621 ms | 3370 ms |
| 优化后 | 43 | 21 个 CSS + ≤8 个图标循环 | 980–1050 ms | 450–490 / 125–140 / 145–165 | 240–310 ms | 3090–3320 ms |
| 关闭所有动效 | 0 | 0 | ≈0 | ≈0 | ≈0 | ≈0 |

“消失”问题：优化后滚到底再滚回来，150 ms 后截图，视口内墓碑全部已画出，0/14 个透明。

结论：中位帧已经回到 60 fps。4× 降速下大约每 10 帧还有 1 帧掉到 30 fps，空闲主线程时间减少 55%，合成层减少 75%。

## 剩下的成本

用拆分实验（每次只关掉一类动画）定位剩余开销：

- **8 个图标循环 ≈ 600 ms / 3 s 主线程**。把 `LOOP_BUDGET` 设为 0 时主线程降到 391 ms。原因是 Motion 对 SVG 子元素的 `transform` 用 JS 每帧写属性，没法交给合成线程。
- **场景 CSS 动画占了大部分 VizCompositor 时间**。关掉全部 CSS 动画后降到约 550 ms。分项（星星合并前测得）：星星约 550 ms、雾约 500 ms、萤火虫约 250 ms、云约 100 ms、蝙蝠约 50 ms。雾是两张 200% 宽的全屏渐变层在平移，面积大。

如果还要继续压，按收益排序：

1. 把 `LOOP_BUDGET` 降到 4–6，或在低端设备（`navigator.hardwareConcurrency <= 4`）上降为 0。
2. 雾层改小（宽度 200% → 130%），或只保留一层。
3. 把图标的整体循环挪到包裹它的 HTML 元素上，用 CSS `@keyframes` 实现，就能交给合成线程。代价是动的会变成整个图标，而不是图标里的某一部分。
4. 给每个分区加 `content-visibility: auto`，减少滚动时的布局和绘制范围。

## 以后加动效的规则

已写进 `.kiro/steering/design-system.md` 的 Motion 一节，要点：

- 循环只动 `transform` / `opacity`，每个图标只有一组在动；`d`、`pathLength`、滤镜只用于入场或悬停。
- 图标循环必须通过 `useLoopSlot` 启动，不另开入口。
- 图标里不放每个实例一份的 `<filter>`。
- 场景里每个无限动画都是一个合成层：新加一个就要拿掉一个；动整个 `<svg>` / `<div>`，不动 SVG 子元素。
- 改完动效用同样的方法重测，并把数字补到本文件。
