1. 为什么选这个方向

为什么是 Costume Contest

评分五项各占 20%：影响力、技术实现、设计、创意、演示。其中设计和演示合占 40%，这正是前端开发者最擅长的部分。Costume Contest 的要求是：应用类型不限，但界面要有能增强功能的诡异设计。它考的是前端完成度，不是后端或架构的广度。

类别对一个人、三周的前端开发者
Costume Contest最合适。主打界面，应用本身可以很小
Resurrection要找到一个"让死技术复活"又足够新颖的点，容易撞车
Frankenstein偏集成与拼装，需要后端和多种技术
Skeleton Crew要交两个独立应用，工作量翻倍

为什么是"依赖墓地"

  • 诡异设计在传达功能：依赖的维护状态用场景来区分（亮灯的墓碑、伸出土的手、飘着的幽灵），信息和装饰是同一件事。这是规则里"增强功能"的字面含义。
  • 评委零门槛：不用登录，不用 API 密钥，没有模型费用。npm 注册表是公开接口。规则要求项目在评审期（到 2027-01-29）对评委免费开放，这个方案天然满足。
  • 有真实用途：依赖老化是前端团队的真实问题，"有人会真的用吗"可以回答"会"。
  • 体量合适：核心是一个页面、一个数据源、一套视觉，一个人三周能做完。
  • 演示上镜：粘贴 → 墓地展开 → 点开一块墓碑，三分钟视频里的流程很清楚。
需要正视的竞争点：依赖健康检查类工具已经不少（npm outdated、Snyk、Bundlephobia 等）。这个项目不靠"检测得更准"取胜，而靠"把枯燥的信息变成一眼能读懂、让人记住的场景"。所以不要把时间花在扩展检测维度上，花在视觉、动效和体验上。

2. 产品设计

用户流程

  1. 打开首页：一句话说明、一个文本框、一个"用示例试试"按钮（评委一键进入）。
  2. 粘贴 package.json（或点示例）。
  3. 页面解析 dependencies 和 devDependencies，逐个查询 npm。
  4. 墓地逐块"长出来"：查询结果一到，对应的墓碑就出现（流式展示，不是等全部完成）。
  5. 顶部汇总："42 个依赖：28 活着，6 僵尸，3 幽灵，5 已死。"
  6. 点击任意墓碑，打开详情：最后发布时间、近一周下载量、deprecated 原因、墓志铭，以及"可以考虑的替代"。

四种状态

活着最近有发布
墓碑亮着灯
僵尸很多人在用
但很久没人维护
幽灵被官方标记
deprecated
已死多年没更新
下载量也很低

判断规则（初稿，阈值要用真实数据校准）

状态规则（按顺序判断）
幽灵最新版本带有 deprecated 字段。优先级最高
活着最近 12 个月内有发布
僵尸超过 12 个月没发布，但近一周下载量仍高（初定 ≥ 100,000）
已死其余情况：超过 12 个月没发布，下载量也不高

注意：很多成熟的小库（如 ms）本来就几乎不更新，但完全可用。"没更新"不等于"有问题"，所以文案要用"静止"、"安息"，而不是"危险"、"有漏洞"。详情面板里写明"这只是维护活跃度，不是安全审计"。

范围：先做什么，后做什么

优先级功能
必做粘贴 package.json 解析；示例数据；四种状态判断；墓地渲染；详情面板；汇总栏；移动端可用；键盘可操作；prefers-reduced-motion
应该做墓志铭文案（先用模板，不调模型）；按状态筛选；分享用的静态截图或链接；加载中的"挖坟"动画
可选支持 pnpm-lock.yaml 或 package-lock.json 看传递依赖；"替代方案"建议；音效（默认静音）
不做登录、账号、数据库、安全漏洞扫描、自动改文件。范围一大，视觉打磨的时间就没了

3. 技术方案

建议的栈

  • Next.js（App Router）+ React + TypeScript + Tailwind：和你已经熟悉的一致。部署到 Vercel。
  • 不用数据库：结果只在浏览器里。
  • 渲染：墓碑用内联 SVG，雾和光用 CSS 渐变与伪元素。数量大时（几百个依赖）再考虑 canvas。
  • 测试：Vitest；状态判断用属性测试（fast-check）。

数据来源（需要先验证）

GET https://registry.npmjs.org/<package>
  → 完整包信息：time[版本] 发布时间、dist-tags.latest、versions[x].deprecated

GET https://api.npmjs.org/downloads/point/last-week/<package>
  → { downloads: number }

开工前先花半小时验证这几件事，别靠假设：

  • 浏览器能否直接调用上面两个接口（CORS）？不行就加一个 Next 路由 /api/package/[name] 转发，并设置缓存。
  • 完整包信息对大包可能很大（版本历史很长）。看实际体积；太大就在服务端只提取需要的几个字段再返回。
  • 下载量接口对作用域包（@scope/name）和批量查询的支持情况。
  • 是否有限流，以及一次并发请求多少个合适（建议限制并发 6–8 个）。

验证结果写进 spec 的"设计"部分，别让 Kiro 凭印象写。

需要特别处理的边界

  • 版本写法不是版本号：workspace:*、file:../x、git+https://…、npm:other@1。这些要识别并显示为"本地/私有"，不要去查 npm。
  • 包不存在（404）、私有包、网络错误、被限流：每种都要有对应的墓碑或提示，不能静默消失。
  • 粘贴的内容不是合法 JSON，或缺少依赖字段：给出清楚的提示。
  • 请求竞态：用户连续粘贴两次，旧请求的结果不能写进新墓地（用 AbortController 加按批次的 key）。

4. 视觉与无障碍

视觉方向

  • 一个场景，不是一堆卡片：深紫黑色夜空、远处的树影、前景的雾；墓碑错落排布，像真的墓地，而不是网格。
  • 状态靠形状和动作区分，不只靠颜色：亮灯、伸出的手、半透明飘动、刻字。
  • 克制的动效：墓碑"长出来"的错落入场、灯光的缓慢呼吸、幽灵的轻微漂浮。动效服务于信息，不抢信息。
  • 文案有声音：汇总栏、空状态、错误提示都用统一的"守墓人"口吻，但关键信息保持清楚。

无障碍（评审"设计"和"影响力"都会看）

  • 所有信息都有文字版：每块墓碑有 aria-label（"react-scripts，僵尸，最后发布于 2022 年 4 月"）；另外提供一个"表格视图"切换，给读屏用户和想看清单的人。
  • 键盘：Tab 逐块切换，方向键在墓地里移动，Enter 打开详情，Esc 关闭；焦点样式清晰。
  • prefers-reduced-motion：关闭漂浮、呼吸和入场动效，只保留静态画面。
  • 对比度：正文和小字对比度不低于 4.5:1（暗色背景上的灰字最容易不达标）。
  • 触屏：墓碑点击区域不小于 44px；手机上改为单列滚动或可平移的画布。

5. Kiro 使用计划

规则明确说"使用 Kiro 不足会被取消资格"，评分里"技术实现"还专门看你对 Kiro 功能的理解深度。关键是真的用，并且一边做一边记录，最后写成说明。

Kiro 功能在这个项目里怎么用最后能写的内容
Spec 拆成 4–5 份：parse-package-json、fetch-package-health、classify-package、graveyard-scene、detail-panel。每份先写需求，再写设计，再生成任务 spec 怎么拆；与"凭感觉对话"相比，哪里更好、哪里更慢
Steering design-system.md（色板、字体、动效规则）、accessibility.md（上面的无障碍清单）、copy-voice.md（守墓人口吻和禁用词）、tech.md（栈和约定） 哪一份 steering 对产出质量影响最大
Hooks 保存时跑类型检查和 lint；改了 classify 相关文件时自动跑属性测试；提交前检查 .kiro 没被忽略 自动化了哪些流程，省了什么
属性测试（PBT） 状态判断：①单调性：同一个包，越久没更新，状态不会变得更"活"；②幽灵优先：只要带 deprecated，必为幽灵；③穷尽性：任意输入都得到四种状态之一；④解析：任意合法 JSON 的依赖键都不丢。用 fast-check PBT 抓到了哪些单元测试想不到的情况（要真跑出来再写）
MCP 用 Fetch 类 MCP 让 Kiro 直接读 npm 注册表文档与真实响应，再据此写类型；如果有设计稿工具的 MCP 也可以试 MCP 让哪件事变容易了
Powers / 自定义 agent 先看有没有适合的 power（前端、测试方向）；可以做一个"无障碍审查"自定义 agent，每次改完界面让它按清单检查 用了哪些、各自的作用；没用的就别写
IDE / CLI IDE 用来走 spec 流程，CLI 用来批量重构和跑检查 两者怎么分工
记录方法：在 .kiro/ 之外放一个 docs/kiro-log.md，每次用 Kiro 做了什么就记三行：做了什么、Kiro 的表现、你改了什么。三周下来就是"Kiro 使用说明"的原始素材。
诚实原则：只写真正用过的功能。评委会看仓库，写了没用的会扣分，不如少写几项但每项讲透。

6. 第一份 spec 草稿（可直接交给 Kiro 细化）

Kiro 的需求文档习惯用 EARS 句式（WHEN … THE SYSTEM SHALL …）。下面是 parse-package-json 的需求草稿：

# Requirements: Parse package.json

## User story
As a front-end developer, I want to paste my package.json and see my
dependencies listed, so that I can check their health.

## Acceptance criteria
1. WHEN the user submits text THEN the system SHALL parse it as JSON.
2. WHEN the text is not valid JSON THEN the system SHALL show a readable
   error and keep the user's text in the box.
3. WHEN the JSON has "dependencies" or "devDependencies" THEN the system
   SHALL return each entry as { name, range, kind }, where kind is
   "dependency" or "devDependency".
4. WHEN the JSON has neither field THEN the system SHALL say that no
   dependencies were found.
5. WHEN a range starts with "workspace:", "file:", "link:", "git",
   "http" or contains "/" in a git-like form THEN the system SHALL mark
   the entry as "non-registry" and SHALL NOT query npm for it.
6. WHEN a range is "npm:other@1" THEN the system SHALL query the aliased
   package name.
7. WHEN the same name appears in both fields THEN the system SHALL keep
   one entry and mark it as "dependency".
8. WHEN the input is larger than 1 MB THEN the system SHALL refuse it with
   a clear message.

## Properties to test (fast-check)
- Parsing never throws for any string input.
- Every dependency key in a valid input appears exactly once in the output.
- Output order is stable for the same input.

9. 风险与应对

风险应对
npm 接口不能直接从浏览器调用，或响应过大第一天验证；准备服务端转发路由，只返回需要的字段并缓存
被 npm 限流，评委演示时失败"用示例试试"使用内置的快照数据，不实时请求；实时查询失败时给出明确提示和重试
只好看、没有用处汇总栏和筛选必须扎实；详情里给出可执行的下一步（"建议关注的替代"）；视频里讲清楚"为谁、解决什么"
视觉做不完先做一个静态但完整的场景（一种状态），再逐个加状态与动效。任何时刻都保持可部署
"没更新"被误解为"不安全"文案明确区分"维护活跃度"和"安全"；不使用"危险"、"漏洞"等词
Kiro 使用说明写不出内容第一天起就记 docs/kiro-log.md；每个功能至少走一次 spec
同类项目撞车差异化放在场景和体验上，不放在检测深度上
最后一天出事故12/3 前完成全部提交材料并保存草稿；12/4 只留作缓冲

11. 提交材料草稿（英文）

One-line pitch

Paste your package.json and watch your dependencies turn into a graveyard: who is alive, who is a zombie, who is a ghost, and who is long dead.

Description skeleton 
## Problem
Front-end projects quietly accumulate dependencies that nobody maintains.
Checking each one by hand is tedious, so it rarely happens.

## What it does
Dependency Graveyard turns a package.json into a graveyard scene. Each
dependency is a tombstone whose look shows its maintenance status:
- Alive: published in the last 12 months
- Zombie: no release for a year, but still widely downloaded
- Ghost: officially deprecated on npm
- Dead: no release for a year and few downloads
Click a tombstone to see the last release, weekly downloads and the
deprecation reason. A table view and keyboard navigation make the same
information available without the visuals.

## Why the spooky design matters
The scene is the interface: status is read from shape and motion, not
only from color, and the summary bar and filters work like a legend.

## Built with
Next.js, React, TypeScript, Tailwind, Vitest, fast-check. No database,
no login, no API keys. Data comes from the public npm registry.

12. 开工第一天

  1. 建新仓库（GitHub 公开），选 MIT 或你决定的许可证，生成 LICENSE。
  2. 初始化 Next.js + TypeScript + Tailwind + Vitest + fast-check。
  3. 建 .kiro/steering/，先写 tech.md 和 design-system.md。
  4. 在 Kiro 里新建第一份 spec（上面第 6 节的草稿），让 Kiro 细化需求，再进入设计和任务。
  5. 写一个 30 行的小脚本或测试，真实请求 3 个 npm 包，确认字段、体积和 CORS。把结果写进 spec 的设计部分。
  6. 建 docs/kiro-log.md，记下今天第一条。
  7. 第一次提交，之后每天都提交，保持提交历史清晰。
